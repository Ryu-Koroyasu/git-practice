\chapter{GitHub編 —ローカルとクラウドをつなぐ—}

第1章では「自分のPCの中だけ」で変更を記録しました。この章では、その記録を \textbf{GitHub（クラウド）} に置いて、バックアップ・複数PC・複数人での共有ができるようにします。

扱うのは「ローカルとGitHubをつなぎ、同期するところまで」です。ブランチを分けた共同作業・プルリクエスト（PR）・コンフリクトの解決は、別冊『チームで安全に開発する』で扱います。

\begin{warnbox}
この章は、\textbf{GitHubアカウントの作成と \cmd{gh auth login} でのログインが済んでいる前提}で進みます。まだの人は、先に別冊『セットアップ編』を済ませてください。ターミナルで \cmd{gh auth status} を実行して \cmd{Logged in to github.com} と表示されれば準備OKです。
\end{warnbox}

\begin{hintbox}
\textbf{この章の読み方}
\begin{itemize}[leftmargin=1.4em, nosep]
  \item まず一度つないでみたい人 → 「リモートリポジトリを用意する」→「つなぐ」を順に写経
  \item アカウント作成・ログインがまだの人 → 別冊『セットアップ編』へ
  \item コマンドをド忘れした人 → 『逆引きチートシート』へ
  \item エラーが出て困った人 → 『トラブルシューティング』へ
\end{itemize}
\end{hintbox}

\section{そもそもGitHubとは}

\textbf{Git と GitHub は別物です。}

\begin{itemize}[leftmargin=1.4em]
  \item \textbf{Git} … あなたのPCの中で動く「変更履歴を記録する道具」（第1章で使ったもの）
  \item \textbf{GitHub} … Gitのリポジトリを\textbf{クラウド上に置いて共有できるWebサービス}
\end{itemize}

第1章では、PCの中に「倉庫（ローカルリポジトリ）」を作りました。GitHubは、その\textbf{クラウド上にあるもう一つの倉庫（リモートリポジトリ）}です。手元の倉庫の写しをクラウドにも置いておくイメージです（図\ref{fig:local-remote}）。

\begin{numfig}{ローカルとリモートは「同期」でつながる2つの倉庫}{fig:local-remote}
\begin{tikzpicture}
  \node[flownode, fill=gitRed, text width=3.2cm] (L)
        {あなたのPC\\ローカルリポジトリ\\{\scriptsize（手元の倉庫）}};
  \node[flownode, fill=gitBlue, text width=3.2cm, right=4.5cm of L] (R)
        {GitHub\\リモートリポジトリ\\{\scriptsize（クラウドの倉庫）}};
  \draw[{Latex[length=3.6mm,width=3mm]}-{Latex[length=3.6mm,width=3mm]},
        line width=1.8pt, draw=black]
        (L) -- (R) node[edgelabel, midway, above] {同期};
\end{tikzpicture}
\end{numfig}

クラウドに置くと、こんなことができます。

\begin{itemize}[leftmargin=1.4em]
  \item \textbf{バックアップ}：PCが壊れても、GitHubから取り戻せる
  \item \textbf{複数PCで共有}：研究室のPCと自宅のPCで同じ作業を続けられる
  \item \textbf{複数人で共有}：チームで同じリポジトリを編集できる
  \item \textbf{公開}：コードや手引書を世界に公開できる
\end{itemize}

なお、\textbf{「リモート（remote）」はクラウド側、「ローカル（local）」はあなたのPCの中}を指す言葉です。この2つは以降ずっと出てくるので、ここで押さえておいてください。

\section{ローカルとリモートの全体像}

ローカルとリモートの間で写しをやり取りするコマンドは、主に次の4つです。\textbf{向き（アップロードかダウンロードか）}で整理すると分かりやすいです（図\ref{fig:remote-overview}）。

\begin{numfig}{ローカルとリモートをつなぐ4つのコマンドと向き}{fig:remote-overview}
\begin{tikzpicture}
  \node[flownode, fill=gitRed, text width=3cm, minimum height=2.2cm] (L)
        {ローカルリポジトリ\\{\scriptsize（あなたのPC）}};
  \node[flownode, fill=gitBlue, text width=3cm, minimum height=2.2cm, right=7cm of L] (R)
        {リモートリポジトリ\\{\scriptsize（GitHub）}};
  \draw[flowarrow] ([yshift=7mm]L.east) -- ([yshift=7mm]R.west)
        node[edgelabel, midway, above] {git push};
  \draw[flowarrow] ([yshift=0mm]R.west) -- ([yshift=0mm]L.east)
        node[edgelabel, midway, above] {git pull / git fetch};
  \draw[flowarrow, dashed] ([yshift=-7mm]R.west) -- ([yshift=-7mm]L.east)
        node[edgelabel, midway, below] {git clone（最初の1回）};
\end{tikzpicture}
\end{numfig}

\begin{center}
\begin{tabularx}{\linewidth}{@{}l l X@{}}
\toprule
コマンド & 向き & 何をするか \\
\midrule
\cmd{git clone} & リモート → ローカル & リモートの倉庫を\textbf{丸ごと手元に複製}する（最初の1回だけ） \\
\cmd{git push} & ローカル → リモート & 手元のコミットを\textbf{クラウドへアップロード}する \\
\cmd{git pull} & リモート → ローカル & クラウドの最新を\textbf{取得して手元に反映}する \\
\cmd{git fetch} & リモート → ローカル & クラウドの最新を\textbf{取得するだけ}（手元には反映しない） \\
\bottomrule
\end{tabularx}
\end{center}

ここで大事なのは、\cmd{git add} / \cmd{git commit}（第1章）が\textbf{ローカルの中だけ}の操作だったという点です。\textbf{GitHubと通信するのは、この \cmd{clone} / \cmd{push} / \cmd{fetch} / \cmd{pull} のときだけ}です。

\section{リモートリポジトリを用意する}

GitHub上に、写しを置くための空の倉庫（リモートリポジトリ）を作ります。

\begin{enumerate}[leftmargin=1.6em]
  \item GitHub右上の \textbf{「+」} → \textbf{New repository}、または自分の \textbf{Repositories} ページにある緑色の \textbf{「New」} ボタンをクリックします。
\end{enumerate}

\screenshot[0.85]{02_github/new_repo.png}{リポジトリの作成ボタン（Repositories ページの「New」）}

\begin{enumerate}[leftmargin=1.6em, start=2]
  \item 次を設定します。
    \begin{itemize}[leftmargin=1.4em, nosep]
      \item \textbf{Repository name}：リポジトリ名（例：\cmd{git-practice}）
      \item \textbf{Public / Private}：公開するか非公開か（研究用途なら通常 \textbf{Private}）
      \item \textbf{Add a README file}：\textbf{チェックしない}（後述のパターンBで既存ローカルをつなぐとき、手順が増えるため）
    \end{itemize}
  \item \textbf{Create repository} をクリックします。
\end{enumerate}

\screenshot[0.85]{02_github/new_repo_setting.png}{作成するリポジトリの設定}

作成後の画面に\textbf{リポジトリのURL}が表示されます。次の手順で使うので、この画面を開いたままにしておきます。

どちらのパターンでも\textbf{リポジトリのURL}が必要です。リポジトリのトップ画面にある緑色の \textbf{「＜＞ Code」} ボタン（作りたての空リポジトリなら \textbf{「Quick setup」} 画面）から、\cmd{https://github.com/\ldots.git} の形のURLをコピーします。

\subsection{パターンA：GitHubで作って \texttt{git clone}（これから始める人向け）}

GitHub上のリポジトリを、丸ごと手元に複製します。作業したいフォルダの\textbf{親フォルダ}で実行してください（リポジトリ名のフォルダが新しく作られます）。

\begin{codebox}[bash]
\begin{code}
git clone https://github.com/your-name/git-practice.git
\end{code}
\end{codebox}

複製が終わると \cmd{git-practice} フォルダが作られ、その中に入れば作業を始められます。\textbf{\cmd{origin}（リモートの登録）も自動で設定される}ので、以降はすぐ \cmd{push} / \cmd{pull} できます。

\begin{codebox}[bash]
\begin{code}
cd git-practice
git remote -v   # origin が登録されていることを確認
\end{code}
\end{codebox}

\subsection{パターンB：既存のローカルを \texttt{push}（第1章で作ったものを上げる）}

第1章で \cmd{git init} して作った手元のリポジトリを、後からGitHubにつなぐ場合です。リポジトリのフォルダ内で実行します。

\begin{codebox}[bash]
\begin{code}
# 1. リモート（origin）を登録する
git remote add origin https://github.com/your-name/git-practice.git

# 2. 登録内容を確認する（origin が2行表示されれば成功）
git remote -v

# 3. 現在のブランチ名を main に統一する
git branch -M main

# 4. 初回のアップロード（-u で「送り先」を覚えさせる）
git push -u origin main
\end{code}
\end{codebox}

\begin{itemize}[leftmargin=1.4em]
  \item \textbf{\cmd{origin}} は「リモートリポジトリの標準的な別名」です。以降 URL の代わりに \cmd{origin} と書けます。
  \item \textbf{\cmd{-u}} は、送り先（\cmd{origin} の \cmd{main}）を「既定の送り先」として覚えさせるオプションです。一度付けておけば、\textbf{次回からは \cmd{git push} / \cmd{git pull} だけ}で同期できます。
\end{itemize}

\begin{warnbox}
\cmd{git remote add origin \ldots} で \cmd{error: remote origin already exists.} と出たら、既に登録済みです。URLを付け替えたいときは \cmd{git remote set-url origin <新しいURL>} を使います。
\end{warnbox}

\section{アップロードする（push）}

\cmd{git push} は、\textbf{ローカルのコミットをリモートへ送る}操作です。第1章の「編集 → add → commit」で記録した内容を、クラウドへ反映します（図\ref{fig:push-flow}）。

\begin{numfig}{編集からクラウド反映までの流れ}{fig:push-flow}
\begin{tikzpicture}
  \node[flownode, fill=gitRed] (E) {編集};
  \node[flownode, fill=gitOrange, right=2.2cm of E] (S) {ステージング};
  \node[flownode, fill=gitGreen, right=2.4cm of S] (L) {ローカル\\リポジトリ};
  \node[flownode, fill=gitBlue, right=2.4cm of L] (R) {GitHub\\リモート};
  \draw[flowarrow] (E) -- (S) node[edgelabel, midway, above] {git add};
  \draw[flowarrow] (S) -- (L) node[edgelabel, midway, above] {git commit};
  \draw[flowarrow] (L) -- (R) node[edgelabel, midway, above] {git push};
\end{tikzpicture}
\end{numfig}

\begin{codebox}[bash]
\begin{code}
# 初回（-u で送り先を覚えさせる）
git push -u origin main

# 2回目以降はこれだけでOK
git push
\end{code}
\end{codebox}

\cmd{push} が終わったら、GitHubのリポジトリ画面を再読み込みしてみてください。コミットしたファイルがクラウド上に表示されているはずです。

\begin{warnbox}
\textbf{コミットしていない変更は \cmd{push} されません。} 手元の編集をクラウドに反映したいときは、必ず先に \cmd{git add} → \cmd{git commit} してから \cmd{git push} します。
\end{warnbox}

\section{ダウンロードする（pull と fetch）}

別のPCや他の人がリモートを更新したとき、その最新を手元に取り込むのが \cmd{git pull} です。

\begin{codebox}[bash]
\begin{code}
# リモートの最新を取得して、手元の main に反映する
git pull
\end{code}
\end{codebox}

\subsection{pull と fetch の違い}

\cmd{git fetch} と \cmd{git pull} は、どちらも「クラウドの最新を取ってくる」コマンドですが、\textbf{手元に反映するかどうか}が違います。カギは、\cmd{git pull} が\textbf{2つの操作をまとめて}行っている点です（図\ref{fig:pull-fetch}）。

\begin{enumerate}[leftmargin=1.6em]
  \item \textbf{取ってくる（fetch）}：クラウド（リモート）の最新を手元に取得する
  \item \textbf{反映する（merge）}：取ってきた内容を、手元の \cmd{main} に合体させる
\end{enumerate}

\cmd{git fetch} は、このうち\textbf{①だけ}を行います。最新を取ってくるものの、\textbf{手元の \cmd{main} や編集中のファイルはまだ変えません}。取ってきた内容は \cmd{origin/main}（＝「リモートが今どうなっているか」を指す手元の目印）に入るので、\textbf{反映する前に中身を確認}できます。

②の\textbf{反映}は、正しくは\textbf{マージ（merge）}といいます。マージは\textbf{2つの流れを1つに合流させる}操作で、ここでは「クラウドで進んだ分」を「手元の \cmd{main}」に合流させて追いつかせています。ふだんは手元がそのまま最新に追いつくだけなので、難しく考える必要はありません。ただし\textbf{同じファイルの同じ箇所を、クラウド側と手元で別々に変更していた場合}は、どちらを採用するか決められず\textbf{コンフリクト（競合）}が起こります。その直し方は、別冊『チームで安全に開発する』で扱います。

\begin{numfig}{git pull は fetch と反映（merge）をまとめて行う}{fig:pull-fetch}
\begin{tikzpicture}
  \node[flownode, fill=gitBlue, text width=2.6cm] (G) {GitHub\\{\scriptsize（リモート）}};
  \node[flownode, fill=gitOrange, text width=2.9cm, right=3.2cm of G] (O) {origin/main\\{\scriptsize（手元の目印）}};
  \node[flownode, fill=gitGreen, text width=2.6cm, right=3.2cm of O] (M) {手元の main};
  \draw[flowarrow] (G) -- (O) node[edgelabel, midway, above] {(1) git fetch};
  \draw[flowarrow] (O) -- (M) node[edgelabel, midway, above] {(2) 反映(merge)};
  \draw[flowarrow, dashed] (G) to[out=-32, in=-148]
        node[edgelabel, midway, below] {git pull （(1)＋(2)）} (M);
\end{tikzpicture}
\end{numfig}

つまり、\textbf{一言でいうと次の関係}です。

\begin{center}
\textbf{git pull ＝ git fetch ＋ 反映（merge）}
\end{center}

\begin{center}
\begin{tabularx}{\linewidth}{@{}l c c@{}}
\toprule
& \cmd{git fetch} & \cmd{git pull} \\
\midrule
クラウドの最新を取ってくる & ○ & ○ \\
手元の \cmd{main} に反映する & ×（まだ反映しない） & ○ \\
主な用途 & 反映前に中身を確認したいとき & ふだんの「最新に追いつく」操作 \\
\bottomrule
\end{tabularx}
\end{center}

\textbf{ふだんは \cmd{git pull} で十分}です。\cmd{git fetch} は「取り込む前に、何が変わったか先に確認したい」ときに使います（\cmd{git fetch} → \cmd{git log origin/main} で確認 → 問題なければ \cmd{git pull}）。

\begin{hintbox}
\textbf{作業を始める前に \cmd{git pull}} を習慣にすると、手元を常に最新の状態から始められ、トラブルが起きにくくなります。
\end{hintbox}

\begin{notebox}
新しめのGitでは、\textbf{初めて \cmd{git pull} したとき}に「取り込み方（merge か rebase か）」の設定を促されることがあります。迷ったら、標準の merge 方式にする次の設定を1度だけ実行しておけば、以降は聞かれません。
\begin{codebox}[bash]
\begin{code}
git config --global pull.rebase false
\end{code}
\end{codebox}
\end{notebox}

\section{日常のフロー}

GitHubとつないだ後の、毎日の基本的な流れです。\textbf{始めにpull、終わりにpush}を挟むだけで、第1章の黄金フロー（編集 → add → commit）がそのまま使えます（図\ref{fig:daily-flow}）。

\begin{numfig}{日常のフロー：pull → 編集 → add → commit → push の繰り返し}{fig:daily-flow}
\begin{tikzpicture}[scale=1.15, transform shape]
  \node[flownode, fill=gitBlue] (P) {git pull\\{\scriptsize 最新を取り込む}};
  \node[flownode, fill=gitRed, right=2.6cm of P] (E) {編集};
  \node[flownode, fill=gitGreen, right=2.6cm of E] (C) {git commit};
  \node[flownode, fill=gitBlue, right=2.6cm of C] (U) {git push\\{\scriptsize クラウドへ反映}};
  \draw[flowarrow] (P) -- (E);
  \draw[flowarrow] (E) -- (C) node[edgelabel, midway, above] {git add};
  \draw[flowarrow] (C) -- (U);
  \draw[flowarrow] (U) to[out=-30, in=-150]
        node[edgelabel, midway, below] {繰り返す} (P);
\end{tikzpicture}
\end{numfig}

\begin{codebox}[bash]
\begin{code}
# 1. 作業開始前に、GitHub（リモート）の最新を手元に取り込む
git pull

# 2. ファイルを編集したら、変更を記録する（第1章の黄金フロー）
git add .                      # 変更をステージングに追加
git commit -m "変更内容のメモ"   # コミットとして記録

# 3. 記録した変更を GitHub（リモート）へアップロードする
git push
\end{code}
\end{codebox}

この繰り返しで、手元とクラウドが常に同期された状態を保てます。

\section*{この章のまとめ}
\addcontentsline{toc}{section}{この章のまとめ}

\begin{itemize}[leftmargin=1.4em]
  \item \textbf{Git（手元の道具）と GitHub（クラウドのサービス）は別物}。GitHubはローカルリポジトリの「もう一つの倉庫」
  \item リモートとの通信は \textbf{\cmd{clone} / \cmd{push} / \cmd{fetch} / \cmd{pull}} の4つ
  \item \cmd{push} する前に \textbf{\cmd{gh auth login}} で1度だけログインしておく（別冊『セットアップ編』）
  \item つなぎ方は2パターン：\textbf{GitHubから始めるなら \cmd{clone}}、\textbf{手元を上げるなら \cmd{remote add} + \cmd{push -u}}
  \item 日常は \textbf{「\cmd{pull} → 編集 → \cmd{add} → \cmd{commit} → \cmd{push}」} の繰り返し
\end{itemize}

これで、1人でGitHubを使う基本はひと通り揃いました。チームでブランチを分けて開発したくなったら、別冊『チームで安全に開発する』へ進んでください。
